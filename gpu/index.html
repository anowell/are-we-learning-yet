GPU & Accelerators

This hub answers two questions. Driving a GPU from Rust is the older half, where the maintained wrappers live; the whole pre-2022 generation below them is dead, and is listed only so you stop finding it first.

Writing the kernel itself in Rust is the newer half, and it is moving in the open: a 2026 paper describes GPU compilation built into rustc and the LLVM backends rather than bolted beside themSource 1: arXiv 2608.13759, and NVIDIA publishes two Rust kernel tracks of its own while saying both are early-stage and neither is production-readySource 2: NVIDIA Developer Blog. Promising, and not yet something to stand on.

Kernel languages & GPU compilers partial

Writing the kernel itself in Rust rather than driving one from it. Rust can now compile to the GPU,Source 1: Drehwald et al. and NVIDIA ships Rust tracks inside CUDA while saying plainly that neither is production-ready.Source 2: NVIDIA

Featured: Rust-GPU/rust-gpu [repo]

A rustc codegen backend that compiles ordinary Rust to SPIR-V, so a compute kernel is a Rust function you can also run and test on the CPU — which is the property no shading language gives you. Through SPIR-V it reaches Vulkan, and through naga, Metal and WebGPU. The costs are real and stated by its own maintainers: it pins a specific nightly, debugging across the compilation layers is hard, and its project blog has been quiet since 2025-08 while the writing moved to VectorWare. Use CubeCL if you want the same portability on stable Rust.

Featured: NVlabs/cuda-oxide [repo]

NVIDIA Labs compiling standard Rust to PTX — not a DSL and not a macro: a rustc codegen backend routes #[kernel] functions through MIR, the third-party pliron IR framework and LLVM, so the kernel is ordinary Rust that rustc understands, and the GPU dialects NVIDIA wrote on top of pliron live in this repository. Together with cuTile it is the first first-party vendor investment in Rust for GPUs, which is a different kind of signal from a community project reaching the same place — but NVIDIA's own announcement puts cuTile first and this second, as the track you drop to when you want to manage threads and memory yourself. It is early alpha by NVIDIA's own description, pins a specific nightly, still needs unsafe for shared memory, is driven by a cargo oxide subcommand you install from the repository, and is not on crates.io — the crates.io name cuda-oxide is an unrelated dead 2021 driver wrapper by someone else.

cuda-oxide is a Rust-to-CUDA compiler that lets you write (SIMT) GPU kernels in safe(ish), idiomatic Rust. It compiles standard Rust code directly to PTX — no DSLs, no foreign language bindings, just Rust.

Featured: cubecl [crate · repo · docs]

Write a kernel once in Rust and compile it to CUDA, ROCm/HIP, Metal, Vulkan, WebGPU or SIMD CPU. Nothing in Python does this — Triton is NVIDIA and AMD only — and it is what makes Burn portable across vendors from one codebase, which is the single strongest argument for Rust on the GPU. It runs on stable Rust, unlike rust-gpu, Rust-CUDA and cuda-oxide, which each pin a different nightly. Two caveats it states itself: the public API is alpha with breaking changes between minor versions, and WebGPU has no tensor-core acceleration.

Multi-platform high-performance compute language extension for Rust.

Featured: cutile [crate · repo · docs]

NVIDIA Labs' tile-based kernel DSL on CUDA Tile IR — and the strongest vendor endorsement any part of the Rust ML stack has ever received. You say what one tile of data does and the compiler decides how many real threads back it, so there is no thread indexing and no shared memory to get wrong; ownership is what makes that safe, because a mutable tensor has to be partitioned into disjoint pieces before it can be launched at all, and the classic aliasing mistake is a borrow error on the host rather than a race on the device. It runs on stable Rust with no nightly and no LLVM of your own, which is the practical difference from cuda-oxide, NVIDIA's other track. Its authors report 7 TB/s element-wise throughput and 2 PFlop/s GEMM on B200, roughly 96% of cuBLAS. Treat those as the project's own numbers; the accompanying paper is where the methodology is; the README carries the hardware and toolkit it needs. It is new, NVIDIA-only, and calls itself early and API-unstable. The reception is worth knowing before you invest: the paper drew real interest, but NVIDIA's own announcement of the two tracks landed on almost nobody — four Hacker News submissions, twelve points at best, not one comment between them, against the 424 points and 118 comments the cuda-oxide repository drew in May. The loudest reaction is a reservation rather than enthusiasm: that a Rust GPU story tied to one vendor's hardware is not the one people were waiting for. Outside NVIDIA the usage is narrow and not arm's length — mistral.rs carries a directory of cuTile kernels behind an optional feature, and its maintainer co-authored the cuTile paper.

cuTile Rust lets programmers safely author and execute tile kernels directly in Rust.

Vendor runtimes & portable compute comprehensive

Driving a GPU from Rust: vendor runtimes, and the portable compute APIs layered over them. The current generation is maintained and shipping inside production software; the pre-2022 generation of wrappers below it is not.

Featured: wgpu [crate · repo · docs]

One compute and graphics API across Vulkan, Metal, DirectX 12, OpenGL and the browser, and by download volume the most-used GPU crate in this catalog. For machine learning it is the portable floor: if you write WGSL against wgpu, it runs on NVIDIA, AMD, Intel, Apple and in a browser without a vendor SDK — which is why Burn's WebGPU backend and Brush's in-browser Gaussian-splat training exist. The ceiling is real too: no tensor cores through WebGPU, and Firefox still ships it disabled by default.

Cross-platform, safe, pure-rust graphics API
